# Final onsite mock：让收据解析服务值得上线

这是依据你提供的 working-session 描述设计的模拟题，不是 Reducto 真题。允许 AI coding、查文档和使用开源库。面试官考察的是你对任务、数据、实验和交付的判断，不要求背框架 API。

## 你的角色和业务目标

你加入了一支文档理解团队。客户上传收据图片，希望自动提取购买明细、税额和总金额，供后续系统处理。团队有一个预训练 VLM 和能运行的初版推理/训练代码，但还没有证明这套方案满足客户需求。

你的任务是在一天内：建立可信 baseline，识别最重要的错误，完成一次模型训练实验和至少一个有依据的改进实验，将选定方案接入推理接口，并在 17:30 向 ML 团队解释是否值得上线。

不要预设模型一定需要微调，也不要把运行成功等同于质量提升。即使没有改进成功，也应交付可信的负面结论、原因和下一步。

## 已有资产

- 模型：Qwen/Qwen2.5-VL-3B-Instruct，固定 revision，支持图像到文本。
- 训练库：Hugging Face TRL 的 SFTTrainer + Transformers + PEFT，基于官方 VLM SFT 示例适配。
- 数据：CORD-v2 的真实印度尼西亚收据，官方划分为 train 800 / validation 100 / test 100。少量标注字段为多值，starter 将它们隔离到 excluded.jsonl，而不猜测单值答案；必须在报告中说明覆盖率。原始 JSON 含语义和 OCR 标注；本题推理时只允许图片和固定任务说明作为输入。
- 提供：下载与标注映射、prompt、语言注意力 LoRA、批量生成、评分、错误浏览 HTML、本地 FastAPI 演示。
- baseline 起点：低图像 token 预算、greedy generation、固定 JSON schema。没有人为植入 bug，也没有提前选定需要你发现的问题。
- 硬件：假设可以使用一张常见 Colab CUDA GPU；两张卡是可选资源，不是要求。单卡显存是否足够必须通过真实 smoke run 确认。

## 输入输出契约

输入是一张收据图片。输出必须为以下 JSON，字符串保留原始数字分隔符、大小写和数量单位，不自行补算：

```json
{
  "items": [
    {"name": "Ice Tea", "quantity": "1 x", "price": "18,000"}
  ],
  "subtotal": null,
  "tax": null,
  "total": "18,000"
}
```

- 没有相应标注的字段为 null；不要用空字符串、0 或猜测值替代。
- items 按印刷顺序排列，包含顶层 menu 项；本题不要求输出 modifier/submenu、现金支付额、找零或其他 CORD 字段。
- price 是标注的行价格，不是 unit price。数量照抄，不能根据总价反推。
- 输出截断、JSON 不合法和 schema 不合格必须记录；不得只在成功样本上算指标。
- schema 有效不代表金额正确，HTTP 200 或 status=ok 也不构成语义质量保证。

## 必须交付

1. 一条别人可以重复运行的 baseline 命令和配置。
2. 数据审查：样本数量、尺寸、目标长度、缺失字段、重复/泄漏风险、代表性样本。
3. 至少一次真实 GPU LoRA 更新，以及保存/重载后的推理验证。只跑随机 tiny-model 不算完成这一项。
4. baseline 与候选方案在同一 validation 集上的比较；说明主要改动和其他固定条件。
5. 至少一个受控改进实验，可以是训练/采样/分辨率/解码/后处理，但不能同时改多个因素后直接归因。
6. 预测 JSONL、指标、运行配置、错误可视化，以及 final adapter（若最终选择使用）。
7. 可运行的推理 CLI 或本地接口，并演示有效输入、坏图片和需要人工复核的输出。
8. 结论：ship / limited rollout / no-go；用证据解释质量、延迟、成本和下一步。

## 评估协议

- train 用于训练；validation 用于迭代；test 在冻结方案后使用一次。不要先查看 test 失败再回头调参。
- 正式比较使用预处理后全部符合 schema 的 validation，另报告相对官方 100 条的覆盖率；先用少量样本验证流程是允许的，但必须标记为 smoke/subset。
- 核心指标：自定义字段 micro-F1、文档 exact match、总金额匹配、JSON/schema 有效率、截断/失败率。
- 字段 F1 比较 `(字段路径, 文本)`，包括 items 的索引，因而对行顺序和漏行敏感。它不是官方 CORD benchmark 分数，也不是 TEDS。
- 金额只做空白标准化，不擅自删除小数点/逗号。说明这种保守标准化与实际业务的差别。
- 缺少预测的样本计失败。评估命令的 manifest 与 limit 必须与推理一致，不准用缩小分母掩盖中途失败。
- 记录样本数和尾延迟估计局限。100 条数据上的 p99 不足以声称生产 SLO。
- 建议与面试官协商上线门槛：例如关键金额字段不能退步，主指标有可解释改善，延迟/失败率在预算内；这里不捏造一个已达到的 baseline 分数。
- 公共模型是否在预训练中见过 CORD 未知。此结果用于实验练习，不证明对新商户或模板的泛化。

## 资源和 AI 使用

单张 T4 16GB 起点是 4-bit NF4 + LoRA r=8、microbatch=1、gradient checkpointing、256 左右图像 token 预算、100 optimizer steps。max_steps=100、梯度累积=8 约对应 800 次样本前后向；不是 100 张图片。

T4 不支持原生 BF16，本代码自动选 FP16；支持 BF16 的 GPU 会使用 BF16。显存还受文本长度、图像 token、优化器和库版本影响，这些是待测起点，不是保证。先跑 2 steps，再决定训练规模。

有两张独立 GPU 时优先并行 baseline/候选评估或不同实验。不要以为两张 16GB 自动变成一张 32GB；本 starter 不提供已验证的多卡 DDP 配置。

AI 可以生成代码、解释 API、辅助 debug。你必须能解释和验证最终代码，记录关键 AI 辅助决策；不能伪造实验或直接将 LLM Judge 当作 ground truth。

## 面试官可能追问

- 为什么选择这个错误类型？为什么不是换更大的模型？
- 为什么训练 loss 下降，生成的 JSON 反而更差？
- 是否存在标注映射错误、截断、重复样本或答案泄漏？
- LoRA 实际训练了哪些参数？图像编码器有没有更新？
- 金额字段提升但明细召回下降，你如何决定是否上线？
- 怎样验证 adapter 确实加载，而不是一直在跑 baseline？
- 如果用户上传的不是收据，你会怎么处理？
